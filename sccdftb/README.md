# SCC-DFTB parameters for the test suite

The `sccdftb` config needs Slater-Koster parameter files. **They are not in this
repository** — they are third-party and carry their own terms — so each test host
supplies them once and `gen_sccdftb_dat.py` builds the index files CHARMM reads.

## What you need on the host

```
$SCCDFTB_DATA/            # default: ~/testing/sccdftb_data
├── skf/                  # the .skf set, obtained separately (~77 MB)
│   ├── C-C.skf
│   ├── ...
│   └── README            # the set's own documentation; keep it
└── sccdftb_*.dat         # generated by gen_sccdftb_dat.py -- do not edit
```

Paths must stay under **64 characters**: `gettab.f` declares
`character*64 skfile` and opens with `status='unknown'`, so a longer one is
truncated into a newly created empty file and fails at EOF rather than saying
the name was too long. The generator refuses to write a file that would trip
this.

Get the `.skf` set from <https://dftb.org/> (the testcases here were written
against **3ob**, the third-order set for organic and biological systems). You
accept the terms there; that is why the files are not redistributed here.

`charmm-test` exports `SCCDFTB_DATA` and runs the generator before `test.com`,
so a normal `charmm-test test sccdftb` needs nothing beyond the `skf/`
directory. To do it by hand:

```bash
export SCCDFTB_DATA=$HOME/testing/sccdftb_data
python3 sccdftb/gen_sccdftb_dat.py
```

## Why generated and not committed

The `.dat` files name their `.skf` files by **absolute path**, so a committed
copy is only ever right on one machine. That is exactly how this broke: the
`sccdftb_data/sccdftb.dat` in use pointed at `/opt/jenkins_data/skf`, a path
that exists on the Jenkins host and nowhere else, so every `sccdftb` testcase on
the cluster aborted looking for its parameters. Generating them per host removes
the failure mode rather than re-encoding it.

## How the testcases find the files

Each one reads the environment variable and builds a path:

```
genv sccdftbdir SCCDFTB_DATA
cats sccdat @sccdftbdir "/sccdftb_CHO.dat"
...
SCCDFTB ... DATF @sccdat
```

`DATF` is the keyword that lets a script name the parameter file instead of
requiring `./sccdftb.dat` in the working directory. Note that `genv` on an
**unset** variable is a level-0 warning, which terminates the run at the default
BOMLEV — so a missing `SCCDFTB_DATA` shows up as `ABNORMAL TERMINATION` two
lines into the test, with nothing about parameters in the message. That was the
whole cause of the 15 `sccdftb` failures on the cluster.

## Element order matters

The order in the filename is the order in the file, and it must match the
`WMAIN` values the testcase assigns to its QM atoms, because CHARMM uses `WMAIN`
as an index into the element list. `c43test/malon_mcec.inp` sets `WMAIN` 1=C,
2=H, 3=O and asks for `sccdftb_CHO.dat`.

Getting this wrong does not fail loudly. The run completes, having assigned the
wrong element to every atom.

## What the generator cannot produce

| file | needed by | why not |
| --- | --- | --- |
| `sccdftb_ONCH.dat` | 19 testcases | **they disagree about what belongs in it** — see below |
| `sccdftb_CHQ.dat` | `c34test/sccdftb_qmmm` | needs a `Q` species for the `QQ*` link atoms |
| `sccdftb_CH_spin.dat` | `c37test/sccdftb_spin-qmmm` | needs spin constants (`spin-c`, `spin-h`); the test's own comment specifies mio-1-1, not 3ob |
| (l-dependent) | `c39test/sccdftb_ldep` | needs l-dependent Hubbard values and spin constants for **Cu**, which is not in the 3ob set at all |

### Why `sccdftb_ONCH.dat` is deliberately not generated

Nineteen testcases read that one filename and do not agree on its contents:

| testcase | declares | wants |
| --- | --- | --- |
| `c33test/h4o2_*`, `c30test/neb_scc`, `c30test/split_scc`, and 12 others | 4 types | O, N, C, H — matches the name |
| `c39test/dxl_bomd_test1` | 4 types | **C, H, N, O** |
| `c40test/sccdftb_cpe` | **2 types** | O, H |
| `c32test/sccgsbp4_2cba` | **5 types** | O, N, C, H, **Zn** |

CHARMM takes the type count from `WMAIN` and indexes this list by it. A file
that suits the first group is read by `sccdftb_cpe` as a 2x2 table off the
first four path lines, and by `sccgsbp4_2cba` as missing an element — and
neither says so. The run finishes and the numbers are quietly wrong, which is
worse than the abort we have today.

Fifteen tests would be served correctly, but not at the price of silently wrong
physics in the other four. The fix is to give each testcase a file matching its
own `WMAIN` order — most cleanly by having each one name a file it owns, rather
than nineteen sharing one name.

`test/data/*.sccdftbdat` in the CHARMM tree holds the authors' original examples
for several of these, including the spin constants — but they reference `.spl`
files under someone else's home directory, and their Hubbard values are from an
older set (O −0.14, C −0.08 against 3ob's −0.1575, −0.1492). Reconciling those
is unfinished work.

## Before trusting the numbers

These testcases mostly compare against captured values rather than checking
anything themselves — 33 of the 35 `sccdftb` tests do not self-report — and the
captured values came from whichever parameter set each author used. Running them
on 3ob will produce numbers, but not necessarily the authors' numbers, and
nothing in the suite would notice the difference.

So do not promote a benchmark for these until they check something
parameter-set-independent. Six of them already call `test first`, which compares
CHARMM's analytic gradient against its own finite-difference gradient and so
holds for any parameter set — but four use `tol 0.0` or no tolerance at all
(with `tol 0.0` the count of agreeing components is identically zero, because
the comparison is `.GE. TOL`), and two are commented out. Converting those is
the cheapest first step.
